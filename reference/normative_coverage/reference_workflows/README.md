# Эталонные процедуры кассовой работы по открытым нормам РК

**Версия 2 · 17.10.2026.** Развёрнуты **80 из 80 тем** каталога в отдельные процедуры: 241 шагов действий и проверки. Сохранены восемь общих маршрутов первой версии. Это нормативная модель для разметки и проверки; утверждение её как внутреннего регламента ForteBank не подтверждено.

**Начать здесь:** [все 80 процедур](topics.md) · [матрица покрытия 80/80](topic_coverage.md) · [JSON для системы](workflows.json) · [проверка результата](validation.json).

Полнота 80/80 означает наличие процедуры для каждой темы текущего каталога. Она не означает 80 обученных детекторов, доказанность нарушений или полноту всего законодательства. Документальные проверки, требования к системам и незакрытый вопрос немедленной блокировки экрана сохранены в соответствующих категориях.

Каталог законов отвечает на вопрос «какое требование действует». Эти процедуры добавляют «при какой операции, кто и что должен сделать, какие есть условия и исключения». Данные о фактических действиях берутся только из проверяемой записи и подтверждённого контекста.

## Как устроен эталон

Для каждой операции указаны условия применения, ожидаемые действия, ссылки на нормы, наблюдаемость и альтернативные ветки. Нумерация ниже помогает читать процедуру. Она сама по себе не означает запрета любого иного порядка: прямые требования до/после вынесены в отдельный блок.

Для шага используются статусы **выполнен**, **есть противоречащий факт**, **не наблюдается/данных недостаточно**, **не применим**. Последние два статуса не являются доказанным нарушением и не добавляют третий итоговый вердикт в обязательный API кейса.

**Пропуск обязательного действия** можно оценивать только при установленной операции, применимой обязанности, отсутствии исключения и достаточной видимости всего нужного этапа. Нельзя считать пропуском действие, которое могло произойти до начала ролика, за кадром или в системе.

**Применимость:** Подтверждена операция приёма наличных от клиента, а не выдача, служебный пересчёт или приём запломбированной инкассаторской сумки.

- `count_check` → `reconcile_amount`. **Логическая зависимость:** Сверка с фактически принятой суммой требует результата приёма и пересчёта; это зависимость данных, а не запрет параллельно проверять реквизиты. [НБРК №231, пункт 19](https://adilet.zan.kz/rus/docs/V1900019680#z104).

**Условие на протяжении операции:** Принимать и пересчитывать деньги в присутствии клиента; ранее принятые деньги хранить в специальных устройствах, закрывающихся на ключ. [НБРК №231, пункт 20](https://adilet.zan.kz/rus/docs/V1900019680#z111). Нужно различать текущую и прежние операции. Пункт не устанавливает, что рабочий сейф должен быть закрыт в каждый момент совершения операции.

**Условие на протяжении операции:** При нескольких приходных документах принимать деньги отдельно по каждому документу. [НБРК №231, пункт 21](https://adilet.zan.kz/rus/docs/V1900019680#z113). Несколько стопок не доказывают несколько документов; нужна идентификация операций.

**Условие на протяжении операции:** Не покидать рабочее место до окончания обслуживания клиента. [НБРК №231, пункт 22](https://adilet.zan.kz/rus/docs/V1900019680#z114). Пункт находится в порядке приёма наличных. Факт незавершённого обслуживания и применимость операции должны быть установлены.

**Ветка:** Установлены сомнительность банкнот либо признаки подделки. Перейти к процедуре [suspect_cash](#suspect_cash). Сомнение зрителя по внешнему виду не равно результату проверки платёжности.

## Как использовать при обучении и проверке

1. Подтвердить вид операции и подходящую редакцию нормы.
2. Для каждого применимого шага разметить наблюдение, временной интервал, кадры и ограничения видимости. Проверяющий подтверждает метку; текст закона сам по себе её не создаёт.
3. Сохранять отдельно примеры правильного выполнения, подтверждённого отклонения и недостаточной наблюдаемости. Не размечать скрытые проводки или подлинность банкнот по догадке.
4. Сравнивать события с условиями и зависимостями процедуры. Проверять возможные альтернативные ветки до постановки метки отклонения.
5. Проверять результат на отложенных записях; дубликаты и фрагменты одной записи не разносить между обучением и проверкой.

Поля будущей разметки перечислены в `expected_record_fields` файла [workflows.json](workflows.json). Сами видеозаписи здесь не просматривались и новые фактические метки не создавались.

## Границы версии

- Модель восстановлена из публичных норм; не является утверждённым внутренним регламентом ForteBank.
- Дата съёмки неизвестна. Перед применением следует выбрать редакцию нормы, действовавшую на дату события.
- Порядок отображения шагов — удобный маршрут чтения. Сам по себе он не создаёт юридического запрета переставлять действия. Явные зависимости отмечены отдельно.
- Условия, ветки, адресаты и исключения проверяются до вынесения результата. Требования к работодателю и заведующему не приписываются кассиру.
- Отсутствие действия в коротком фрагменте не доказывает пропуск: нужны наблюдаемые начало, конец и зона выполнения соответствующего этапа.
- Нечитаемые документы, учёт, полномочия и результаты проверки денег не восстанавливаются предположениями.
- Внутренний статус unknown/not_observed не меняет обязательную схему API; он нужен для исключения необоснованных положительных заключений.
- Все 80 тем каталога развёрнуты в отдельные процедуры и связаны с исходными пунктами; восемь общих маршрутов сохранены. Полнота этой структуры не означает наблюдаемость каждого требования по видео или закрытие всех вопросов применимости.

Источники США/Европы не использованы для установления обязательных шагов этих процедур. Х-28 остаётся с неподтверждённой применимостью конкретного правила немедленной ручной блокировки к рабочей системе кассира.
